# Roadmap 10. Frontend MVP

Следующий этап после завершения backend stabilization и testing expansion.

## Цель

Собрать первый полноценный frontend для `TableBooker`, который:

- работает с уже готовым backend;
- закрывает основной пользовательский flow;
- остаётся достаточно простым, чтобы его реально закончить;
- выглядит аккуратно и современно, но не превращается в бесконечный дизайн-проект.

На этом этапе хотим получить:

- отдельное `Next.js` приложение в том же репозитории;
- понятную структуру frontend-кода;
- рабочий auth-flow;
- рабочий booking-flow;
- удобный MVP UI, на который уже не стыдно смотреть;
- базу, которую можно дальше развивать без полного переписывания.

## Почему это следующий шаг

Backend уже выглядит достаточно зрелым:

- `auth-service`, `booking-service`, `notification-service`;
- `gRPC`, `Redis`, `RabbitMQ`;
- email / phone auth;
- notification flow;
- автоматические тесты;
- CI.

То есть следующий естественный этап — не наращивать backend ради backend, а дать проекту пользовательский интерфейс.

## Почему frontend пока лучше делать в этом же репозитории

На этом этапе не хотим сразу разносить проект на отдельные репозитории.

Плюсы текущего подхода:

- backend и frontend остаются рядом;
- проще поднимать всё локально;
- проще синхронизировать API и UI;
- проще вести roadmap и README;
- быстрее дойти до рабочего результата.

Отдельный репозиторий можно сделать позже, если это действительно понадобится.

## Что не хотим делать

На этом этапе не хотим:

- строить слишком тяжёлую frontend-архитектуру;
- тратить недели на идеальный дизайн-системный слой;
- добавлять глобальный state manager без реальной необходимости;
- делать полноценную админку;
- строить realtime, websocket-и, optimistic updates everywhere;
- пытаться закрыть все возможные edge-case UX до первого живого интерфейса.

Сначала нужен законченный, понятный и удобный MVP.

## Базовый стек

На старте хотим использовать:

- `Next.js`;
- `React`;
- `TypeScript`;
- `Tailwind CSS`;
- `TanStack Query`;
- `React Hook Form`;
- `Zod`.

### Почему `TanStack Query`

Потому что у проекта много server state:

- current user;
- restaurants;
- tables;
- my bookings;
- login / register / create booking / confirm / cancel mutations.

Без `TanStack Query` это тоже можно сделать, но код быстро станет более ручным и хрупким.
На этом проекте `TanStack Query` даёт хорошую практическую ценность почти сразу.

## Архитектурная идея

Хотим сделать frontend не “максимально академическим”, а практичным.

Базовая идея:

- `Next.js` app в этом же monorepo;
- App Router;
- простой, понятный слой API-клиентов;
- server state через `TanStack Query`;
- формы через `React Hook Form` + `Zod`;
- локальный UI state без Redux;
- структура по смыслу, а не ради модного шаблона.

То есть хотим избежать двух крайностей:

- “всё навалено в одну папку”;
- “слишком сложная enterprise-структура для маленького MVP”.

## Предлагаемая структура

Один из спокойных вариантов:

- `apps/web`
- `apps/web/src/app`
- `apps/web/src/shared`
- `apps/web/src/shared/api`
- `apps/web/src/shared/lib`
- `apps/web/src/shared/types`
- `apps/web/src/shared/ui`
- `apps/web/src/features/auth`
- `apps/web/src/features/restaurants`
- `apps/web/src/features/bookings`

Это не догма, но как стартовая структура она выглядит достаточно здоровой.

## Step 1. Create Next.js App Inside Monorepo

### Что делаем

Добавляем новое frontend-приложение в этот же репозиторий.

### Что важно

- не отдельный репозиторий;
- отдельное приложение внутри monorepo;
- TypeScript;
- App Router;
- ESLint;
- Tailwind.

### Предполагаемое расположение

- `apps/web`

### Definition of Done

- в репозитории появился frontend-app;
- он запускается локально;
- структура проекта не конфликтует с существующим backend.

## Step 2. Setup Frontend Foundation

### Что делаем

Настраиваем базовый технический фундамент.

### Что входит

- подключение `TanStack Query`;
- подключение `React Hook Form`;
- подключение `Zod`;
- базовый API client;
- env для frontend;
- базовый layout;
- базовая навигация.

### Что важно

Не нужно сразу строить сложный SDK.
Достаточно сделать ясный и поддерживаемый слой вызова backend API.

### Definition of Done

- frontend умеет обращаться к backend;
- есть базовый layout и routing shell;
- проект готов к добавлению страниц и форм.

## Step 3. Build Auth Flow

### Что делаем

Реализуем весь минимально нужный auth-flow.

### Что входит

- register page;
- login page;
- logout action;
- получение current user;
- хранение и подстановка `accessToken`;
- поддержка логина и регистрации через:
  - `email`
  - `phone`
  - `email + phone`

### Что важно

- формы должны быть понятными;
- ошибки backend должны отображаться нормально;
- auth-flow не должен выглядеть “сырой заглушкой”.

### Definition of Done

- пользователь может зарегистрироваться;
- пользователь может войти;
- пользователь может выйти;
- frontend понимает, авторизован пользователь или нет.

## Step 4. Build Restaurants Browsing Flow

### Что делаем

Добавляем пользовательский read-flow по ресторанам.

### Что входит

- главная страница;
- список ресторанов;
- страница одного ресторана;
- список столов ресторана;
- понятная навигация между этими экранами.

### Что важно

- не нужен сложный каталог;
- нужен чистый и удобный browsing flow;
- loading / empty / error states должны быть оформлены.

### Definition of Done

- пользователь может зайти в приложение;
- увидеть рестораны;
- открыть ресторан;
- увидеть его столы.

## Step 5. Build Booking Creation Flow

### Что делаем

Добавляем создание брони из интерфейса.

### Что входит

- форма создания брони;
- выбор столика;
- ввод гостей;
- ввод даты и времени;
- отправка запроса в backend;
- отображение success / error states.

### Что важно

- не нужно строить сложный календарный продукт;
- сначала нужен просто удобный рабочий booking form;
- валидация должна быть понятной и не раздражающей.

### Definition of Done

- пользователь может создать бронь из UI;
- ошибки API читаемо отображаются;
- happy path работает от начала до конца.

## Step 6. Build My Bookings Flow

### Что делаем

Добавляем экран “мои брони”.

### Что входит

- список броней текущего пользователя;
- отображение статусов;
- confirm action;
- cancel action;
- обновление данных после mutation.

### Что важно

- это один из главных “замыкающих” экранов всего MVP;
- именно он делает backend ощутимо живым в UI.

### Definition of Done

- пользователь видит свои брони;
- может подтвердить бронь;
- может отменить бронь;
- UI корректно обновляется после действий.

## Step 7. Improve UX And Visual Layer

### Что делаем

На этом шаге не переделываем архитектуру, а доводим интерфейс до приятного состояния.

### Что входит

- единые spacing and typography decisions;
- понятные buttons / inputs / cards;
- аккуратные error states;
- loading states;
- empty states;
- базовая адаптивность для mobile и desktop.

### Что важно

Не нужен “премиальный dribbble clone”.
Но и сырой utilitarian UI тоже не хочется.

Нужен интерфейс, который:

- приятно открыть;
- удобно использовать;
- не мешает показать backend за ним.

### Definition of Done

- интерфейс выглядит цельно;
- MVP не стыдно показать;
- пользоваться им уже удобно.

## Step 8. Connect Frontend And Backend End-To-End

### Что делаем

Проходим все ключевые реальные сценарии через UI.

### Что проверяем

1. register works;
2. login works;
3. current user state works;
4. restaurants loading works;
5. booking creation works;
6. my bookings works;
7. confirm / cancel works;
8. logout works.

### Что важно

Это уже не про отдельные компоненты, а про цельный пользовательский flow.

### Definition of Done

- основные сценарии backend реально работают через frontend;
- frontend и backend ощущаются как единый продукт.

## Step 9. Update Docs And Frontend Run Instructions

### Что делаем

После появления frontend обновляем документацию.

### Что входит

- `README.md`;
- команды запуска;
- описание frontend app;
- env notes;
- краткое описание пользовательских сценариев.

### Definition of Done

- проект понятно запускать;
- frontend отражён в документации;
- repo снова выглядит цельно после нового большого этапа.

## Итог

После завершения этого roadmap проект получит:

- первый полноценный frontend;
- законченный MVP user flow;
- backend + frontend связку в одном репозитории;
- хорошую основу для следующего этапа:
  - polish;
  - deployment;
  - портфолио-подача;
  - дальнейшее развитие продукта.
