# Roadmap 11. Frontend Testing

Этап после MVP, локализации и перехода на `httpOnly` refresh cookie.

## Цель

Добавить для `apps/web` небольшой, понятный и действительно полезный набор frontend-тестов.

На этом этапе не нужна большая тестовая система и не нужен ещё один парк из десятков кейсов ради покрытия. Нужен такой набор тестов, который:

- страхует ключевые пользовательские сценарии;
- помогает учиться и разбираться в качестве;
- не превращает поддержку тестов в отдельный проект.

## Что уже есть на старте

Сейчас у frontend уже есть смысл тестировать, потому что MVP перестал быть пустым:

- есть страницы `login`, `register`, `restaurants`, `restaurant details`, `my bookings`;
- есть booking form с локальной валидацией и сетевым submit;
- есть session flow:
  - `accessToken` хранится в `localStorage`;
  - `refreshToken` живёт в `httpOnly` cookie;
- есть локализация `RU / EN`;
- выбранный язык сохраняется между reload;
- backend уже покрыт отдельным набором unit/e2e тестов.

То есть фронтенд больше не должен держаться только на ручной прокликиваемой проверке.

## Что не является целью этого этапа

На этом roadmap специально не делаем:

- 100% coverage;
- тест на каждый компонент;
- snapshot-тесты ради snapshot-тестов;
- тяжёлый browser e2e-слой;
- дублирование backend e2e на фронтенде.

Идея этапа: покрыть только то, что реально может сломаться и что сложно удерживать в голове без тестов.

## Принцип отбора тестов

Каждый тест должен отвечать хотя бы одному из критериев:

- защищает критический пользовательский flow;
- ловит уже встречавшийся баг;
- фиксирует нетривиальную логику;
- помогает понять архитектуру приложения.

Если тест не делает ни одного из этих пунктов, на этом этапе он не нужен.

## Предлагаемый стек

Спокойный и практичный вариант для текущего проекта:

- `Vitest`;
- `jsdom`;
- `@testing-library/react`;
- `@testing-library/user-event`;
- `MSW` для сетевых сценариев, где это действительно полезно.

`Playwright` и полноценные browser e2e можно вынести в отдельный будущий этап, если они вообще понадобятся.

## Планируемый объём

Нормальная цель для этого этапа:

- примерно `10-18` frontend-тестов;
- без попытки дойти до размеров backend-пака;
- с упором на самые ценные сценарии.

Это уже даст хорошую страховку и при этом останется удобным для изучения и поддержки.

## Step 1. Поднять test setup для `apps/web`

### Что делаем

Добавляем базовую инфраструктуру frontend-тестов.

### Что входит

- конфиг `Vitest` для `apps/web`;
- `jsdom`;
- `Testing Library`;
- общий `setup` файл;
- алиасы и env для тестов;
- один sanity-check test, чтобы убедиться, что setup рабочий.

### Что важно

- запуск должен быть простым;
- setup не должен конфликтовать с `Next.js app router`;
- тесты должны быть изолированы от backend-инфраструктуры.

### Definition of Done

- frontend тесты запускаются отдельной командой;
- базовый smoke test проходит;
- новый тест можно добавить без обходных решений и магии.

## Step 2. Покрыть чистую логику, где тесты самые дешёвые

### Что делаем

Сначала покрываем код, который не требует тяжёлого UI-рендера и даёт максимальную пользу.

### Что именно тестируем

- `apps/web/src/features/bookings/model/booking-schema.ts`
  - выбор доступных временных слотов;
  - логика initial values;
  - базовые validation rules;
- `apps/web/src/features/auth/model/login-schema.ts`
  - `email or phone required`;
  - валидация телефона;
- `apps/web/src/features/auth/model/register-schema.ts`
  - пустой телефон не ломает регистрацию;
  - введённый телефон валидируется;
- `apps/web/src/shared/i18n/locale-storage.ts`
  - чтение и сохранение локали.

### Почему именно это

Это логика, где уже были реальные баги:

- с phone validation;
- с пустым phone в register;
- с booking time rules;
- с сохранением locale.

### Definition of Done

- самые чувствительные helper/schema части зафиксированы тестами;
- уже пойманные баги становятся regression cases.

## Step 3. Покрыть 3 самые важные формы

### Что делаем

Пишем interaction-тесты только для того UI, где пользователь реально вводит данные и где возможны регрессии.

### Что именно тестируем

#### Login

- submit с пустыми полями показывает нужную validation error;
- невалидный телефон показывает локализованную ошибку;
- backend error `Invalid credentials` маппится на нормальное пользовательское сообщение.

#### Register

- регистрация по `email + password` работает, если phone пустой;
- duplicate email / duplicate phone отображаются локализованно;
- невалидный phone показывает локализованную ошибку.

#### Booking form

- submit без обязательных полей показывает нужные ошибки;
- успех показывает локализованное success message;
- после успешного создания форма сбрасывается в ожидаемое состояние.

### Что важно

- тестировать глазами пользователя;
- не зашиваться в декоративную разметку;
- проверять сообщения, submit и реальные эффекты.

### Definition of Done

- ключевые формы покрыты небольшим, но полезным набором interaction-тестов;
- локализованные ошибки и success states зафиксированы.

## Step 4. Добавить 2-4 интеграционных сценария верхнего уровня

### Что делаем

Добавляем не “всё подряд”, а только те сценарии, которые лучше всего проверяют связку страницы, запроса и состояния.

### Приоритетные сценарии

- страница логина:
  - успешный вход сохраняет access token и показывает текущего пользователя;
- страница регистрации:
  - успешная регистрация показывает success message;
- страница бронирования / restaurant details:
  - создание бронирования приводит к success state;
- locale flow:
  - переключение языка сохраняется и используется после reload.

### Что важно

- не уходить в реальный браузер там, где достаточно integration-теста;
- не дублировать backend e2e;
- проверять именно критические точки приложения.

### Definition of Done

- есть минимальный набор тестов на ключевые app-level flows;
- локализация и session-related поведение зафиксированы;
- ручная проверка перестаёт быть единственным способом убедиться, что всё работает.

## Step 5. Встроить frontend tests в обычный workflow

### Что делаем

Доводим этап до состояния, в котором тесты действительно используются, а не лежат “на потом”.

### Что входит

- добавить scripts для frontend tests;
- обновить `README`;
- коротко описать:
  - что именно покрывает frontend test suite;
  - как его запускать;
  - почему набор тестов намеренно ограниченный.

### Definition of Done

- frontend test suite запускается одной понятной командой;
- документация обновлена;
- команде понятно, что здесь проверяется, а что сознательно не покрыто.

## Что будет считаться хорошим результатом этапа

Этап считается успешным, если в конце:

- у `apps/web` появляется собственный рабочий test setup;
- покрыты самые хрупкие и важные flows;
- количество тестов остаётся умеренным;
- тесты помогают учиться и поддерживать проект, а не мешают развиваться дальше.

## Итоговая идея Roadmap 11

Это не этап про “максимум тестов”.

Это этап про:

- разумный минимум;
- высокую отдачу от каждого теста;
- фиксацию текущего качества frontend после MVP, i18n и cookie-based auth.
