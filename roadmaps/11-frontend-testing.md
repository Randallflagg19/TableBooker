# Roadmap 11. Frontend Testing

Следующий этап после завершения frontend MVP.

## Цель

Добавить понятный и полезный набор тестов для `apps/web`, чтобы frontend перестал держаться только на ручной проверке.

На этом этапе хотим получить:

- рабочую test setup для frontend;
- быстрые тесты для утилит и форм;
- тесты на ключевые пользовательские сценарии;
- базовую уверенность, что MVP не ломается от дальнейших правок.

## Почему это следующий шаг

Сейчас frontend уже выглядит законченным как MVP:

- auth-flow работает;
- restaurants flow работает;
- booking creation flow работает;
- my bookings flow работает;
- confirm / cancel работает;
- визуальный слой уже не выглядит как черновик.

То есть следующий естественный шаг — не добавлять новые экраны ради новых экранов, а зафиксировать это тестами.

## Что не хотим делать

На этом этапе не хотим:

- строить слишком тяжёлую тестовую архитектуру;
- покрывать snapshot-тестами каждый компонент подряд;
- тестировать каждый `className`;
- пытаться добиться “100% coverage” ради цифры;
- сразу строить огромный e2e-парк с хрупкими сценариями.

Нужны не “максимальные тесты”, а тесты с хорошей практической пользой.

## Предлагаемый стек

Спокойный и реалистичный вариант:

- `Vitest`;
- `@testing-library/react`;
- `@testing-library/user-event`;
- `jsdom`;
- при необходимости `MSW` для сетевых сценариев;
- позже, отдельно, можно добавить `Playwright` для браузерных e2e.

## Общий подход

Нужны три уровня проверки:

- тесты утилит и схем;
- тесты интерактивных форм и экранов;
- минимальный набор интеграционных сценариев для ключевых пользовательских flows.

То есть не хотим свалиться в крайности:

- “вообще ничего не тестируем”;
- “тестируем абсолютно всё, включая декоративную разметку”.

## Step 1. Setup Frontend Test Foundation

### Что делаем

Поднимаем базовую test infrastructure для `apps/web`.

### Что входит

- установка `Vitest`;
- настройка `jsdom`;
- подключение `Testing Library`;
- базовый `setup` файл;
- env и aliases для тестов;
- первая sanity-check spec.

### Что важно

- тесты должны запускаться просто;
- setup не должен конфликтовать с `Next.js` app structure;
- новые тесты должно быть легко добавлять.

### Definition of Done

- frontend тесты запускаются локально;
- есть рабочий test runner;
- базовый smoke test проходит.

## Step 2. Cover Validation And Helper Logic

### Что делаем

Добавляем тесты на код, который проще и полезнее всего стабилизировать первым.

### Что входит

- `booking-schema`;
- helper-функции времени и даты;
- auth-session helper logic;
- простые utility-функции форматирования, если они остаются отдельно.

### Что важно

- тестировать не реализацию, а поведение;
- покрыть edge cases времени и токенов;
- зафиксировать логику, которая уже оказалась чувствительной к багам.

### Definition of Done

- основные helper-функции покрыты тестами;
- кейсы с валидным / истёкшим токеном проверяются;
- логика booking time filtering проверяется.

## Step 3. Add Form And Screen Interaction Tests

### Что делаем

Проверяем ключевые пользовательские действия на уровне UI.

### Что входит

- login form;
- register form;
- booking form;
- `My Bookings` states:
  - loading
  - empty
  - success
  - error

### Что важно

- проверять поведение глазами пользователя;
- не привязываться слишком жёстко к текущей разметке;
- проверять submit, validation, error display, success states.

### Definition of Done

- формы тестируются через user interaction;
- ошибки отображаются ожидаемо;
- ключевые UI states зафиксированы тестами.

## Step 4. Add Lightweight Integration Coverage

### Что делаем

Проверяем самые важные сквозные куски frontend logic без тяжёлого real-browser e2e.

### Что входит

- login happy path;
- booking creation happy path;
- my bookings refresh after create / confirm / cancel;
- query invalidation checks;
- session continuation through refresh token logic.

### Что важно

- тестировать не все ветки подряд, а самые ценные сценарии;
- использовать моки API осмысленно;
- не дублировать unit tests на другом уровне без пользы.

### Definition of Done

- самые важные frontend flows покрыты интеграционно;
- критические regression points закрыты;
- ручная проверка уже не остаётся единственным способом проверки.

## Step 5. Integrate Frontend Tests Into Daily Workflow

### Что делаем

Встраиваем frontend tests в обычную разработку.

### Что входит

- команды запуска тестов в `README`;
- удобные `package.json` scripts;
- при желании CI integration позже;
- ясное понимание, какие тесты гоняются быстро, а какие реже.

### Что важно

Тесты должны помогать, а не создавать ощущение, что их проще не запускать.

### Definition of Done

- frontend tests удобно запускать локально;
- документация обновлена;
- тесты становятся частью нормального цикла изменений.
