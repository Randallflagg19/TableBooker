# Roadmap 08. Auth Email Or Phone

Следующий этап после завершения `Notifications Providers`.

## Цель

Сделать аутентификацию более жизненной и гибкой:

- пользователь может зарегистрироваться по `email`;
- пользователь может зарегистрироваться по `phone`;
- пользователь может указать оба контакта сразу;
- логин поддерживает те же сценарии;
- при этом API остаётся компактным и не разрастается в отдельные endpoint-ы под каждый способ входа.

## Почему это нужно

Сейчас в проекте уже есть поле `phone` в таблице `users`, но текущий auth-flow практически завязан только на `email`.

Это создаёт разрыв:

- модель данных уже поддерживает телефон;
- notification-flow уже умеет использовать телефон;
- но сам пользователь не может нормально управлять этим каналом через auth API.

## Что не хотим делать

На этом этапе не хотим:

- создавать отдельные endpoint-ы вроде `/auth/register-by-phone`;
- делать OTP / SMS-code login;
- делать подтверждение телефона через SMS-код;
- строить полноценный profile-management модуль.

Сначала хотим просто перейти от `email-only auth` к `email-or-phone auth`.

## Архитектурная идея

Хотим сохранить один и тот же компактный auth API:

- `POST /auth/register`
- `POST /auth/login`

Но сделать DTO и бизнес-логику гибче:

- `email` optional;
- `phone` optional;
- хотя бы одно из них обязательно.

То есть логика будет не “разные endpoint-ы для разных способов входа”, а “один endpoint с несколькими допустимыми сценариями”.

## Step 1. Define Flexible Auth Rules

### Что делаем

Фиксируем правила регистрации и логина.

### Правила

- `password` обязателен;
- для `register` хотя бы одно из `email` или `phone` обязательно;
- для `login` хотя бы одно из `email` или `phone` обязательно;
- можно передать и `email`, и `phone` сразу;
- `email` и `phone` по-прежнему должны быть уникальными.

### Definition of Done

- правила входа и регистрации описаны явно;
- понятно, какие сценарии поддерживаются.

## Step 2. Update Register DTO

### Что делаем

Меняем `RegisterDto`.

### Что важно

- `email` становится optional;
- `phone` становится optional;
- `password` остаётся required;
- добавляется валидация: хотя бы один контакт обязателен.

### Definition of Done

- Swagger показывает гибкий register DTO;
- API не требует только `email`.

## Step 3. Update Login DTO

### Что делаем

Меняем `LoginDto`.

### Что важно

- `email` становится optional;
- `phone` становится optional;
- `password` остаётся required;
- добавляется то же правило: хотя бы один контакт обязателен.

### Definition of Done

- Swagger показывает гибкий login DTO;
- логин можно сделать по `email` или по `phone`.

## Step 4. Update Register Logic

### Что делаем

Переписываем `AuthService.register(...)`.

### Что важно

- если передан `email`, проверяем его уникальность;
- если передан `phone`, проверяем его уникальность;
- можно сохранять только `email`, только `phone` или оба;
- `INSERT` должен корректно работать с `NULL` в одном из полей.

### Definition of Done

- пользователь может зарегистрироваться с `email`;
- пользователь может зарегистрироваться с `phone`;
- пользователь может зарегистрироваться с обоими контактами.

## Step 5. Update Login Logic

### Что делаем

Переписываем `AuthService.login(...)`.

### Что важно

- если передан `email`, ищем пользователя по `email`;
- если передан `phone`, ищем пользователя по `phone`;
- если переданы оба, можно договориться о приоритете или проверить согласованность;
- пароль по-прежнему проверяется как и раньше.

### Definition of Done

- логин по `email` работает;
- логин по `phone` работает;
- логика остаётся предсказуемой.

## Step 6. Review JWT And User Payloads

### Что делаем

Проверяем, не ломает ли новая модель текущие JWT payload и current user flow.

### Что важно

- `email` может быть `null`;
- `phone` может быть `null`;
- существующий flow не должен падать из-за отсутствия одного контакта.

### Definition of Done

- access token flow работает как раньше;
- отсутствие `email` не ломает auth-flow.

## Step 7. Add Tests For New Auth Scenarios

### Что делаем

Добавляем e2e / integration scenarios.

### Минимум

- register with email only;
- register with phone only;
- register with email and phone;
- reject when both email and phone are missing;
- login with email;
- login with phone.

### Definition of Done

- новые auth сценарии покрыты тестами;
- refactor auth-flow становится безопаснее.

## Step 8. Manual Verification

### Что проверяем

1. Пользователь может зарегистрироваться только с `email`.
2. Пользователь может зарегистрироваться только с `phone`.
3. Пользователь может зарегистрироваться с `email` и `phone`.
4. Пользователь может логиниться по `email`.
5. Пользователь может логиниться по `phone`.
6. API корректно отклоняет запрос, если нет ни `email`, ни `phone`.
7. Swagger остаётся понятным и не перегруженным.

### Definition of Done

- auth API стал гибче;
- endpoint-ы не размножились;
- `phone` перестал быть “мертвым” полем в модели.

## Итог

После завершения этого roadmap проект получит:

- более realistic auth flow;
- поддержку регистрации и логина через `email` или `phone`;
- лучшую связку с notification system;
- более жизненную модель пользователя без перегруженного API.
