# Testing Roadmap

План следующего этапа для `TableBooker` после завершения `gRPC` и `Redis` интеграций.

## Цель

Укрепить проект тестами так, чтобы:

- не бояться рефакторинга;
- проверять не только отдельные методы, но и реальные пользовательские сценарии;
- безопасно двигаться к следующим инфраструктурным этапам;
- иметь более зрелый и убедительный backend-проект.

## Почему этот этап важен сейчас

Сейчас в проекте уже есть:

- `auth-service`;
- `booking-service`;
- `gRPC` между сервисами;
- `Redis` для rate limiting и cache.

Это значит, что проект стал заметно сложнее:

- больше точек отказа;
- больше инфраструктурных зависимостей;
- больше сценариев, которые нужно проверять целиком.

Без тестов дальше двигаться можно, но становится неприятно и рискованно.

## Что хотим получить на выходе

После завершения этого этапа проект должен иметь:

- e2e тесты на ключевые HTTP сценарии;
- проверки auth-flow;
- проверки booking-flow;
- проверки Redis use cases;
- минимальные негативные сценарии;
- понятную тестовую базу для следующих шагов.

## Что включаем в тестовый MVP

### Auth Service

Покрыть сценарии:

- `POST /auth/register`;
- `POST /auth/login`;
- `POST /auth/refresh`;
- `POST /auth/logout`;
- `GET /auth/me`.

### Booking Service

Покрыть сценарии:

- `GET /restaurants`;
- `GET /restaurants/:id`;
- `GET /restaurants/:id/tables`;
- `GET /tables/:id`;
- `POST /bookings`;
- `PATCH /bookings/:id/confirm`;
- `PATCH /bookings/:id/cancel`;
- `GET /bookings/my`.

### Redis Use Cases

Проверить:

- rate limiting на auth endpoints;
- cache-поведение на read endpoints booking.

## Step 1. Audit Current Test Coverage

### Что делаем

Смотрим, какие тесты уже есть и что именно они покрывают.

### Definition of Done

- понятно, что уже проверяется;
- понятно, какие сценарии отсутствуют.

## Step 2. Stabilize Test Environment

### Что делаем

Приводим тестовое окружение в предсказуемый вид.

### Что важно

- отдельная тестовая БД;
- понятный `.env.test`;
- Redis доступен в тестовом окружении;
- тесты можно запускать повторяемо.

### Definition of Done

- тестовая среда воспроизводима;
- тесты не зависят от случайного локального состояния.

## Step 3. Add Auth Service E2E Tests

### Что делаем

Добавляем e2e тесты на auth-flow.

### Минимум

- успешная регистрация;
- запрет регистрации с уже существующим email;
- успешный логин;
- ошибка на неверных credentials;
- успешный `GET /auth/me`;
- успешный refresh;
- logout инвалидирует refresh token.

### Definition of Done

- базовый auth-flow проверяется тестами.

## Step 4. Expand Booking Service E2E Tests

### Что делаем

Докрываем booking-flow.

### Минимум

- чтение ресторанов и столов;
- создание брони;
- подтверждение брони;
- отмена брони;
- конфликт бронирования;
- получение броней текущего пользователя.

### Definition of Done

- ключевой booking-flow проверяется end-to-end.

## Step 5. Add Redis-Focused Tests

### Что делаем

Проверяем Redis use cases не только вручную, но и тестами.

### Минимум

- rate limit срабатывает после превышения лимита;
- cache не ломает read endpoints;
- cache miss не ломает ответ;
- при повторном чтении поведение остаётся корректным.

### Definition of Done

- Redis интеграция подтверждена тестами.

## Step 6. Add Negative Scenarios

### Что делаем

Покрываем типичные ошибки и пограничные случаи.

### Примеры

- неверный access token;
- неверный refresh token;
- попытка подтвердить несуществующую бронь;
- попытка создать конфликтующую бронь;
- превышение rate limit.

### Definition of Done

- happy path и важные error path покрыты тестами.

## Step 7. Keep Test Suite Usable

### Что делаем

Следим, чтобы тесты оставались быстрыми и понятными.

### Что важно

- минимум лишнего дублирования;
- хорошие helper-функции;
- понятные названия тестов;
- предсказуемая очистка данных после тестов.

### Definition of Done

- тесты не превращаются в хаос;
- их реально хочется запускать перед изменениями.

## Definition Of Done

Этап тестов можно считать завершённым, когда:

- auth-flow покрыт e2e тестами;
- booking-flow покрыт e2e тестами;
- Redis use cases проверяются не только руками, но и тестами;
- негативные сценарии тоже проверены;
- тесты помогают безопасно развивать проект дальше.
