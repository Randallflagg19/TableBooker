# Roadmap 05. Testing

План завершения тестового этапа для `TableBooker` после внедрения `gRPC`, `Redis` и базового `CI`.

## Цель

Довести тестовый слой до состояния, в котором проект можно безопасно развивать дальше:

- без страха рефакторить;
- с понятным покрытием ключевых сценариев;
- с проверкой не только HTTP endpoint-ов, но и инфраструктурных интеграций;
- с предсказуемым запуском тестов локально и в `GitHub Actions`.

## Что уже сделано

На текущий момент в проекте уже есть:

- e2e тесты на чтение ресторанов;
- e2e тесты на основной booking-flow;
- e2e тесты на auth-flow;
- отдельная тестовая БД;
- Redis в тестовом окружении;
- базовый `CI`, который поднимает инфраструктуру и запускает `yarn test:e2e`.

Это значит, что тестовый этап уже начат хорошо, и дальше не нужно начинать заново.  
Нужно просто последовательно закрыть оставшиеся куски.

## Какой порядок работы дальше

Следующий порядок я считаю самым логичным:

1. добить недостающие HTTP/e2e тесты в `booking-service`;
2. проверить реальный межсервисный `gRPC` flow;
3. добавить тесты на `Redis` use cases;
4. после этого добить негативные сценарии;
5. по ходу поддерживать тесты в аккуратном и поддерживаемом виде.

То есть:

- сначала закрываем обычные пользовательские сценарии;
- потом проверяем интеграции;
- потом добавляем error-path coverage;
- и только после этого считаем тестовый этап закрытым полностью.

`Done`

- чтение ресторанов;

### Definition of Done

- пользовательский booking-flow закрыт полностью.

## Step 5. Add Real gRPC Flow Test

### Статус

`Done`

### Что делаем

Добавляем отдельный тест на реальное взаимодействие `booking-service` и `auth-service` без мока `AuthClientService`.

### Что важно проверить

- пользователь логинится в `auth-service`;
- получает `accessToken`;
- идет с этим токеном в `booking-service`;
- `booking-service` реально вызывает `auth-service` по `gRPC`;
- бронь создаётся от имени текущего пользователя.

### Почему это идёт раньше Redis tests

Потому что `gRPC` — это критичная архитектурная интеграция между сервисами.  
Её полезно зафиксировать отдельным тестом до того, как углубляться в инфраструктурные edge cases Redis.

### Definition of Done

- межсервисный happy path подтверждён тестом;
- booking-flow проверяется не только с моками, но и через реальный `gRPC`.

## Step 6. Add Redis-Focused Tests

### Статус

`Done`

### Что делаем

Проверяем `Redis` use cases уже тестами, а не только руками.

### Минимум

- rate limit срабатывает после превышения лимита;
- cache не ломает `GET /restaurants`;
- cache не ломает `GET /restaurants/:id`;
- cache не ломает `GET /restaurants/:id/tables`;
- cache не ломает `GET /tables/:id`.

### Что важно

На этом этапе не обязательно делать сложные тесты на hit/miss на уровне внутренних вызовов.  
Сначала важно подтвердить, что Redis-интеграция не ломает внешний контракт.

### Definition of Done

- Redis use cases подтверждены тестами;
- auth и booking корректно работают при обычном happy path с Redis.

## Step 7. Add Negative Scenarios

### Статус

`Done`

### Что делаем

Собираем отдельный слой негативных сценариев после того, как happy path уже уверенно покрыт.

### Что сюда входит

- неверный access token;
- неверный refresh token;
- превышение rate limit;
- попытка получить несуществующий стол;
- попытка получить несуществующий ресторан;
- попытка подтвердить несуществующую бронь;
- попытка отменить несуществующую бронь;
- попытка создать конфликтующую бронь, если захочется выделить это в отдельный блок.

### Почему негативные сценарии идут после gRPC и Redis

Потому что сначала нужно зафиксировать, что happy path по всем основным интеграциям работает.  
После этого уже добиваем error-path, чтобы не путать сломанный happy path со сломанным edge case.

### Definition of Done

- важные error path покрыты;
- поведение API в неуспешных сценариях предсказуемо проверяется тестами.

## Step 8. Keep Test Suite Usable

### Статус

`Ongoing`

### Что это значит

Это не отдельный разовый шаг, который можно один раз "сделать и забыть".  
Это правило на весь тестовый этап.

### Что имеется в виду

- не плодить дублирование без смысла;
- выносить полезные helper-функции;
- держать тесты читаемыми;
- чистить данные после тестов;
- избегать хрупких проверок;
- не смешивать в одном тесте слишком много причин для падения.

### Текущее состояние

Сейчас этот пункт у тебя уже выглядит хорошо:

- тесты читаемые;
- helper-функции уже есть;
- очистка тестовых данных есть;
- структура файлов понятная.

Но это не `Done`, а именно `Ongoing`, потому что поддерживать это нужно и в следующих тестах.

### Definition of Done

- тесты остаются поддерживаемыми по мере роста проекта;
- новый тестовый код не превращает suite в хаос.

## Definition Of Done

Тестовый этап можно считать завершённым, когда:

- auth-flow покрыт e2e тестами;
- booking-flow покрыт полностью;
- есть хотя бы один тест на реальный `gRPC` flow;
- Redis use cases подтверждены тестами;
- ключевые негативные сценарии покрыты;
- `CI` стабильно прогоняет тесты на push и pull request.
