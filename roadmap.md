# TableBooker Roadmap

План дальнейшего развития проекта после завершения backend MVP.

## Iteration 1: Stabilize Backend

Цель: закрепить текущий backend и перестать бояться рефакторинга.

### Что делаем

- Добавляем `e2e` тесты на основные пользовательские сценарии.
- Проверяем, что текущее API работает как единое целое, а не только по отдельным методам.

### Первые сценарии для покрытия

- `GET /restaurants`
- `GET /restaurants/:id/tables`
- `POST /bookings`
- `PATCH /bookings/:id/confirm`
- `PATCH /bookings/:id/cancel`
- конфликт бронирования по времени
- поведение `HOLD` при пересечении слотов

### Что это даст

- безопасный рефакторинг
- более сильный портфолио-проект
- удобную базу для внедрения auth и Redis

## Iteration 2: Add Auth Inside Monolith

Цель: сделать backend ближе к реальному продукту, не распиливая его слишком рано.

### Что делаем

- регистрация пользователя
- логин пользователя
- хеширование пароля
- JWT access token
- guards для защищённых маршрутов
- привязка брони к текущему пользователю, а не к `userId` из тела запроса

### Почему это сейчас важно

После этого API станет выглядеть как настоящий backend-сервис:

- пользователь логинится
- получает токен
- ходит в защищённые маршруты
- сервер сам определяет, кто делает бронь

### Что будет потом

Эту логику можно будет вынести в отдельный `auth-service` и связать с booking-сервисом по `gRPC`.

## Iteration 3: Add Redis

Цель: познакомиться с инфраструктурным слоем, который часто используется в backend-разработке.

### Где пригодится Redis

- кэш списка доступных столов
- rate limiting
- временные ключи
- сценарии с refresh token или blacklist токенов

### Как это обычно работает

- `PostgreSQL` хранит основную бизнес-правду
- `Redis` хранит быстрые временные данные
- оба сервиса запускаются через `docker compose`

## Iteration 4: Add Rate Limit

Цель: защитить API от спама и злоупотребления.

### Где полезно ограничение

- логин
- регистрация
- создание брони
- чувствительные публичные маршруты

### Что это даст

- базовую защиту от brute force и спама
- более реалистичную серверную архитектуру

## Later: Service Extraction

Когда монолит станет устойчивым, можно переходить к разделению на сервисы.

### Auth Service

- выносим регистрацию, логин и JWT-логику в отдельное приложение
- связываем с booking-сервисом по `gRPC`

### Notification Service

Нужен для побочных действий, которые не должны ломать основную бизнес-операцию:

- email о подтверждении брони
- email об отмене брони
- напоминание о визите
- позже SMS или push

### RabbitMQ

Добавляем не сразу, а когда появится отдельный сервис уведомлений или другие асинхронные обработчики событий.

Подходящий момент:

- booking-service публикует событие
- notification-service его получает
- отправка уведомления идёт отдельно от основной транзакции
